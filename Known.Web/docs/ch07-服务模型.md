# 第7章 服务模型

服务模型是 Known 的第二条主线。它把“业务接口”“服务端实现”“客户端代理”统一成一套可复用模式，使同一份服务契约可以在 Server、Wasm 和桌面模式下协同工作。

---

## 7.1 核心类型

服务模型的核心定义在 `Known/Service.cs`：

### 7.1.1 `IService`

```csharp
public interface IService
{
    Context Context { get; set; }
}
```

所有前后端交互服务都实现这个接口，统一持有 `Context`。

### 7.1.2 `ClientBase`

`ClientBase` 是客户端基类，主要职责是：

- 持有 `HttpClient`
- 自动把当前用户的 `Known-Token` 加入请求头
- 承载 Wasm 或远程调用模式下的服务代理

### 7.1.3 `ServiceBase`

`ServiceBase` 是服务端业务基类，提供：

- `App`
- `Context`
- `CurrentUser`
- `Language`
- `Database`

这意味着你写业务服务时，很多系统依赖已经是现成的。

---

## 7.2 服务开发标准模式

Known 推荐的服务开发是三段式：

1. 定义接口
2. 实现客户端代理
3. 实现服务端逻辑

示例：

```csharp
public interface IProduceService : IService
{
    Task<PagingResult<TbMaterial>> QueryMaterialsAsync(PagingCriteria criteria);
    Task<Result> SaveMaterialAsync(TbMaterial info);
}

[Client]
class ProduceClient(HttpClient http) : ClientBase(http), IProduceService
{
    public Task<PagingResult<TbMaterial>> QueryMaterialsAsync(PagingCriteria criteria)
        => Http.QueryAsync<TbMaterial>("/Produce/QueryMaterials", criteria);

    public Task<Result> SaveMaterialAsync(TbMaterial info)
        => Http.PostAsync("/Produce/SaveMaterial", info);
}

[WebApi, Service]
class ProduceService(Context context) : ServiceBase(context), IProduceService
{
    public Task<PagingResult<TbMaterial>> QueryMaterialsAsync(PagingCriteria criteria)
        => Database.QueryPageAsync<TbMaterial>(criteria);

    public async Task<Result> SaveMaterialAsync(TbMaterial info)
    {
        var database = Database;
        var model = await database.QueryByIdAsync<TbMaterial>(info.Id);
        model ??= new TbMaterial();
        model.FillModel(info);

        var vr = model.Validate(Context);
        if (!vr.IsValid)
            return vr;

        return await database.TransactionAsync(Language.Save, async db =>
        {
            await db.SaveAsync(model);
            info.Id = model.Id;
        }, info);
    }
}
```

## 7.3 `[Service]` 与 `[Client]`

### 7.3.1 `[Service]`

`[Service]` 用于告诉框架该类需要被注入，生命周期默认为 `Scoped`。框架会在程序集扫描阶段自动注册。

### 7.3.2 `[Client]`

`[Client]` 用于标记客户端代理类。`AddKnownClient()` 会自动扫描并注册这些类，用于 Wasm 或远程模式下的接口调用。

---

## 7.4 `[WebApi]` 的作用

`[WebApi]` 是 Known 服务模型中非常关键的一个特性。它表示该服务类的方法可以被自动暴露为动态 WebApi。

对应运行机制：

1. 宿主调用 `AddKnownWeb()` 或 `AddKnownWebApi()`。
2. `Known.Core` 中的 `ApiFeatureProvider` 把带 `[WebApi]` 的类加入 MVC。
3. 运行时生成可访问的服务接口。

这也是为什么 Wasm 客户端不需要单独维护大量 Controller。

---

## 7.5 `Context` 的意义

Known 的服务模型不是“无状态函数集合”，而是围绕 `Context` 工作。`Context` 通常包含：

- 当前用户
- 当前语言
- 当前请求环境
- 当前应用信息

这让服务天然具备以下能力：

- 根据当前用户判断权限
- 根据当前语言返回本地化消息
- 根据当前租户进行数据隔离
- 根据当前应用切换行为

---

## 7.6 泛型服务与通用服务

框架内置了 `IEntityService<>`、`EntityService<>`、`EntityClient<>` 等通用实体服务类型，适合标准 CRUD 场景。

如果你的业务就是常规增删改查，可优先复用这些泛型服务；如果逻辑更复杂，再单独定义专用接口和实现。

---

## 7.7 典型内置服务

理解框架时，建议优先阅读这些服务：

| 服务 | 作用 |
|------|------|
| `AdminService` | 登录、系统管理、初始化等后台核心能力 |
| `RoleService` | 角色与授权 |
| `ModuleService` | 模块与菜单 |
| `LanguageService` | 多语言 |
| `TaskService` | 后台任务 |
| `ImportService` | 导入处理 |
| `FileService` | 文件与附件 |
| `AutoService` | 低代码页面数据服务 |
| `FlowService` | 工作流引擎 |
| `ChatService` | AI 对话 |
| `WeixinService` | 微信集成 |

这些服务覆盖了 Known 的大部分平台能力面。

---

## 7.8 Server 与 Wasm 下的服务差异

### 7.8.1 Server 模式

页面通常直接创建或注入服务，服务内部直接访问数据库。

### 7.8.2 Wasm 模式

页面拿到的是 `ClientBase` 派生客户端，客户端通过 HTTP 访问后端 `[WebApi]` 服务。

### 7.8.3 为什么同一接口可复用

因为业务页面依赖的是接口而不是具体实现，所以同一页面逻辑在不同宿主下可以由不同实现接管。

---

## 7.9 推荐开发方式

1. 所有业务服务都先定义接口。
2. 需要多端复用时，同时实现 `Client` 和 `Service`。
3. 服务端统一继承 `ServiceBase`。
4. 返回值尽量使用 `Result`、`PagingResult<T>` 等框架标准模型。
5. 把验证、事务、落库放在服务层，不要散落在页面层。

---

## 7.10 常见误区

### 7.10.1 把页面当服务

页面只负责交互和 UI 组织，不应承担复杂业务规则和事务控制。

### 7.10.2 只写服务端不写接口

这样会降低可测试性和多端复用能力。

### 7.10.3 在 Wasm 模式中绕开 `ClientBase`

Known 已经封装了 Token、请求和标准返回模型，除非是第三方 HTTP 调用，否则不建议自己重新封装一套。

## 本章小结

Known 的服务模型本质上是一套“统一契约、双端实现、自动暴露”的服务体系：

1. `IService` 统一上下文。
2. `ServiceBase` 负责服务端逻辑。
3. `ClientBase` 负责客户端代理。
4. `[WebApi]` 让服务自动成为接口入口。

# 第1章 框架概述

Known 是一个基于 Blazor 的全栈业务开发框架，同时也是一个插件化平台底座。它的核心价值不只是“能写页面”，而是把实体模型、数据访问、服务接口、菜单权限、系统模块、低代码页面、插件扩展和多端宿主组织成一套统一开发方式。

---

## 1.1 什么是 Known

从源码结构看，Known 由三层组成：

1. `Known/`：框架核心类库，提供对象模型、数据访问、服务模型、页面基类、系统实体、工作流、AI、微信、插件能力。
2. `Plugins/`：插件项目集合，用于承载系统增强插件和业务插件。
3. `Known.Server`、`Known.Wasm`、`Known.WasmHost`、`Known.WinForm`、`Known.Maui`：不同宿主项目，用同一套核心能力在不同运行模式下工作。

因此，Known 不是单纯的 UI 组件库，也不是一个只有脚手架的模板仓库，而是一套完整的业务开发平台。

---

## 1.2 框架定位

Known 的定位可以概括为四句话：

1. 面向企业级后台和中台系统。
2. 强调插件化和平台化扩展。
3. 强调前后端统一使用 C# 开发。
4. 强调“系统基座 + 业务插件”协作模式。

它特别适合以下项目：

- ERP、OA、CRM、MES、WMS 等管理系统
- 平台化 SaaS 后台
- 低代码或半低代码业务平台
- 希望统一 Web、桌面、移动端宿主的管理系统

它不太适合以下项目：

- 纯静态站点
- 极致图形性能应用
- 大型游戏客户端
- 对前端生态完全依赖 JS/TS 的团队项目

---

## 1.3 设计思路

Known 的源码体现出非常明确的设计思路。

### 1.3.1 约定优于配置

框架大量依赖特性和约定进行自动发现，例如：

- `[Table]` 标识实体映射表
- `[Column]` 和 `[Form]` 定义表格和表单元数据
- `[Service]` 和 `[Client]` 注入服务与客户端
- `[WebApi]` 自动生成接口入口
- `[Menu]`、`[AppMenu]` 生成模块菜单
- `[DevPlugin]`、`[PagePlugin]`、`[NavPlugin]` 注入插件体系

这意味着很多事情不需要手工维护配置表，而是在代码被扫描时自动形成运行时元数据。

### 1.3.2 模块化与插件化

Known 推荐每个业务域以独立插件项目组织，常见结构如下：

```text
Plugins/
├─Known.Core
├─Known.Admin
├─Known.Cells
└─Known.Sample
```

业务系统可以像 `Known.Sample` 一样，把自己的实体、服务、页面、静态资源、工作流和报表样例集中放在一个插件中，再通过扩展方法一次性装配。

### 1.3.3 全栈统一语言

Known 的一个显著特点是前端页面、后端服务、实体模型、验证逻辑、导入导出、工作流回调都使用 C#。这降低了团队在业务开发中切换语言和上下文的成本。

### 1.3.4 内置基座优先

Known 已内置用户、角色、组织、模块、字典、多语言、任务、文件、日志、AI、微信、工作流等系统能力。推荐做法是复用这些基座能力，再叠加业务插件，而不是从零搭一套后台基础设施。

---

## 1.4 核心能力概览

### 1.4.1 实体模型

框架通过 `EntityBase<TKey>` 和 `EntityBase` 统一管理主键、审计字段、租户字段和扩展字段。

```csharp
public class EntityBase : EntityBase<string>
{
    public string CreateBy { get; set; }
    public DateTime CreateTime { get; set; }
    public string ModifyBy { get; set; }
    public DateTime? ModifyTime { get; set; }
    public int Version { get; set; }
    public string Extension { get; set; }
    public string AppId { get; set; }
    public string CompNo { get; set; }
}
```

这套基类决定了 Known 天然适合后台业务场景，因为审计、版本、扩展和平台隔离字段都已具备。

### 1.4.2 数据访问

Known 并不是围绕 EF Core DbContext 工作，而是自带 `Database` 轻量数据访问层，支持：

- 查询、分页、聚合
- 插入、更新、删除
- 事务
- 存储过程
- Schema 和建表支持
- SQLite、SQL Server、MySQL、PostgreSQL、Oracle、达梦、Access 等数据库

### 1.4.3 服务模型

服务模型是 Known 的核心主线之一：

- `IService`：服务统一接口
- `ServiceBase`：服务端基类
- `ClientBase`：客户端基类
- `[WebApi]`：自动暴露服务接口

这种模式使同一个服务接口既可以在 Server 模式下本地注入，也可以在 Wasm 模式下通过 HTTP 自动调用。

### 1.4.4 页面开发

框架提供统一页面基类：

- `BasePage`
- `BaseTablePage<T>`
- `BaseForm<T>`
- `BaseTabPage`
- `BaseStepPage`

这些基类已经把常见的查询、列表、表单、按钮、弹窗、标签页、权限和错误处理封装好了。

### 1.4.5 插件与低代码

Known 的插件体系不仅支持程序集级业务扩展，还支持：

- 顶部导航插件
- 页面区块插件
- 开发中心插件
- 低代码页面装配
- 页面布局配置

`PluginPage`、`PluginBase<T>`、`PluginConfig` 共同构成了可视化页面拼装基础。

### 1.4.6 平台能力

源码中已经提供的高级能力包括：

- 权限与菜单
- 多语言
- 后台任务
- 导入导出
- 工作流
- 微信集成
- AI 对话
- 文件与打印
- 开发中心

---

## 1.5 运行模式

Known 的业务代码可运行在多种宿主下：

| 宿主 | 说明 |
|------|------|
| `Known.Server` | Blazor Server 模式，服务端渲染与交互 |
| `Known.Wasm` | WebAssembly 客户端工程 |
| `Known.WasmHost` | Wasm 的后端宿主，提供 API 和混合渲染 |
| `Known.WinForm` | 桌面端宿主 |
| `Known.Maui` | 移动/跨平台宿主 |

这几种宿主复用的是同一套 `Known` 核心库和插件程序集，差异主要体现在启动装配方式和通信路径。

---

## 1.6 与常见架构的区别

和传统三层架构相比，Known 的区别主要在这里：

1. 元数据直接写在实体和页面上，而不是散落在配置表或前端 JSON。
2. 服务既可以本地调用，也可以自动变成 WebApi。
3. 菜单、权限、插件和页面可以被统一扫描装配。
4. 系统后台不是空壳，而是完整内置模块。
5. 低代码和编码式开发不是互斥关系，而是可以并存。

---

## 1.7 学习建议

学习 Known 最好的顺序不是先啃所有源码，而是按下面路径理解：

1. 先看宿主启动：`Known.Server/Program.cs`、`AppConfig.cs`
2. 再看核心注册：`Known/Extension.cs`
3. 再看实体和数据访问：`Entity.cs`、`Data/Database*.cs`
4. 再看服务模型：`Service.cs`
5. 再看页面基类和内置页面：`Blazor/Base*.cs`、`Pages/*.cs`
6. 最后看插件、开发中心、工作流、AI、微信等高级模块

这条路线最接近实际运行机制。

## 本章小结

本章要记住四个核心结论：

1. Known 是一套插件化全栈业务开发框架，而不是单纯的 UI 库。
2. 它的主线是“实体 + 数据访问 + 服务 + 页面 + 插件 + 系统基座”。
3. 它已经内置了后台系统所需的大部分基础能力。
4. 业务开发的推荐模式是复用基座，再以插件方式扩展。

# 第5章 实体模型

实体模型是 Known 的第一条主线。实体不仅用于数据库映射，还直接参与验证、表格元数据、表单元数据、平台字段隔离和低代码配置。

---

## 5.1 基础实体结构

Known 的实体基类定义在 `Known/Entity.cs` 中，主要有三层：

1. `BaseEntity`
2. `EntityBase<TKey>`
3. `EntityBase`

### 5.1.1 `BaseEntity`

`BaseEntity` 主要负责对象变更跟踪：

- `IsNew` 标识实体是否为新增
- `Original` 保存原始字段值
- `IsChanged` 用于比较属性是否变化

这为通用保存逻辑提供了基础。

### 5.1.2 `EntityBase<TKey>`

这一层主要负责：

- 主键 `Id`
- 默认主键初始化
- `FillModel` 数据回填
- `Validate(Context)` 实体验证

`Validate` 会逐个属性读取验证特性，并汇总成统一的 `Result` 对象。

### 5.1.3 `EntityBase`

字符串主键版本的 `EntityBase` 是业务中最常用的基类，内置字段包括：

- `CreateBy`
- `CreateTime`
- `ModifyBy`
- `ModifyTime`
- `Version`
- `Extension`
- `AppId`
- `CompNo`

这也是 Known 能直接适用于企业后台的关键原因之一。

---

## 5.2 审计字段和平台字段

### 5.2.1 审计字段

审计字段为系统自动记录创建和修改行为提供基础，适用于：

- 数据溯源
- 操作审计
- 版本控制
- 列表页展示

### 5.2.2 `AppId`

`AppId` 用于标识实体属于哪个系统或应用。对于平台化系统或多子系统部署，这是一个重要标识。

### 5.2.3 `CompNo`

`CompNo` 是租户或企业编码。Known 在平台模式下会围绕它进行数据隔离，文档和业务设计时不应忽略这一字段。

### 5.2.4 `Extension`

`Extension` 是一个 JSON 扩展字段，适合承载少量不固定属性，而不必频繁改表结构。

---

## 5.3 实体声明方式

### 5.3.1 表映射

实体通常使用 `[Table]` 声明数据库表名：

```csharp
[Table("TbMaterial")]
public class TbMaterial : EntityBase
{
}
```

### 5.3.2 列元数据

`[Column]` 既描述字段，也描述列表页行为。常见属性有：

- `Field`
- `IsVisible`
- `IsQuery`
- `IsSort`
- `IsSum`
- `Type`
- `Category`
- `Width`
- `Align`
- `IsViewLink`

因此 `[Column]` 并不只是数据库映射属性，更像是表格页面的元数据定义。

### 5.3.3 表单元数据

`[Form]` 负责定义表单表现：

- 行列位置：`Row`、`Column`
- 字段类型：`Type`
- 自定义字段：`CustomField`
- 是否只读：`ReadOnly`
- 占位符：`Placeholder`
- 默认值：`FieldValue`
- 文本域行数：`Rows`

这让编码式表单和低代码表单可以共享一套模型。

---

## 5.4 一个典型实体示例

```csharp
public class TbMaterial : EntityBase
{
    [Required]
    [MaxLength(50)]
    [Column(Width = 150, IsQuery = true, IsViewLink = true)]
    [DisplayName("客户料号")]
    public string CustGNo { get; set; }

    [Column]
    [DisplayName("备注")]
    public string Note { get; set; }

    public List<PackFieldInfo> PackFields { get; set; } = [];
}
```

这种定义会同时影响：

- 数据库存储
- 查询栏生成
- 列表页显示
- 表单布局

---

## 5.5 实体验证

Known 的实体验证入口是：

```csharp
public virtual Result Validate(Context context)
```

校验过程会：

1. 遍历当前实体属性
2. 读取属性上的验证特性
3. 结合当前语言对象生成错误信息
4. 汇总为 `Result`

因此，Known 的验证不是孤立的，而是和语言、多端显示、服务返回模型统一在一起。

## 5.7 实体与页面、服务的关系

在 Known 中，一个实体通常会同时服务于三类对象：

1. 数据层：数据库表与查询
2. 服务层：参数、返回结果、保存逻辑
3. UI 层：列表列、表单项、查询条件

这是一种高度统一的对象模型设计。优点是开发效率高，缺点是实体定义需要更谨慎，因为它往往会影响多个层面。

---

## 5.8 业务设计建议

### 5.8.1 优先继承 `EntityBase`

除非你的主键不是字符串或有特殊需求，否则优先使用 `EntityBase`，可以直接获得平台字段和通用行为。

### 5.8.2 谨慎使用 `Extension`

`Extension` 很适合小规模扩展，但不应把核心业务字段长期堆进 JSON，否则会影响查询和维护。

### 5.8.3 将 `Column` 和 `Form` 当作 UI 元数据

这两个特性会直接影响页面表现，应和前端需求一起设计，而不是只从数据库角度考虑。

### 5.8.4 学会复用系统实体设计风格

如果不确定业务实体该怎么定义，优先参考：

- `SysUser`
- `SysDictionary`
- `SysTask`
- `Plugins/Known.Sample/Entities/*`

## 本章小结

实体模型在 Known 中承担了比普通 ORM 实体更重的职责：

1. 它是数据库模型。
2. 它是页面元数据来源。
3. 它参与验证和平台字段管理。
4. 它也是低代码和代码生成的重要输入。
